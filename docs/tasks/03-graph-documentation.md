# Task 3: Graph Documentation

## Description

Write documentation under `docs/graph/` describing the knowledge graph's architecture, staleness rules, quality standards, and seeding strategy. This documentation serves as the canonical reference for how the graph is constructed, maintained, and validated.

## Actions

### 3.1 Create docs/graph/architecture.md

**File:** `docs/graph/architecture.md`

Describe:
- The two subgraphs (codebase and knowledge) and how they relate
- Node types (codebase: File, Function, Class, Module, Config, Table, Endpoint; knowledge: Domain, Feature, Operation, Actor, BusinessRule, Entity, Decision, Constraint)
- Relationship types grouped by category (structural, behavioral, product/business, PO interview, bridge)
- The `kind` property separation strategy
- Mermaid diagram of the full graph or key sub-graphs
- The `IMPLEMENTED_BY` bridge and its role
- ID conventions for each node type
- Key query patterns (examples from neo4j-schema.md)
- Index and constraint strategy

### 3.2 Create docs/graph/outdating-rules.md

**File:** `docs/graph/outdating-rules.md`

Describe:
- The graph is derived knowledge — it is derived from source code and PO interviews
- When the codebase changes, the codebase subgraph is rebuilt (nodes with `kind: "codebase"` are wiped and regenerated by `/grasp`)
- When PO knowledge changes, `/grasp-domain` or `/grasp-po` must be re-run to update the knowledge subgraph
- The `status` property on `Feature`, `Operation`, `BusinessRule` (`"planned" | "implemented" | "partial"`) signals staleness — a `"implemented"` feature that no longer has `IMPLEMENTED_BY` edges to existing code is stale
- `IMPLEMENTED_BY.status` (`"legacy" | "target" | "shared" | "planned"`) signals whether a knowledge node's implementation is current
- Conditions under which a node should be considered stale:
  - A codebase node whose file no longer exists on disk
  - A knowledge node whose `IMPLEMENTED_BY` targets have been deleted or renamed
  - A `planned` node that has become `implemented` but old `planned` entries remain
- How staleness is detected (queries, scripts)
- How staleness is resolved (re-run relevant skill, manual update, deletion)

### 3.3 Create docs/graph/quality-rules.md

**File:** `docs/graph/quality-rules.md`

Describe:
- The graph should be safer and more useful than a search index — it must prevent wrong assumptions
- Quality dimensions: correctness, completeness, freshness, consistency
- Rules for node quality:
  - Every `Feature` must have at least one `HAS_OPERATION` relationship or an explicit `summary` explaining why it has no operations
  - Every `Operation` must have a `summary` — no empty or placeholder summaries
  - Every `Actor` referenced by `PERFORMED_BY` or `RESTRICTED_FOR` must have at least one permission or restriction documented
  - `IMPLEMENTED_BY` confidence must be >= 0.5 — below this threshold, the mapping should be flagged for review
  - No orphaned knowledge nodes (nodes with no incoming or outgoing relationships except for `DECIDES`/`CONSTRAINED_BY`)
- Rules for relationship quality:
  - `SEQUENCE` chains must not contain cycles
  - `IMPLEMENTED_BY` targets must exist as nodes in the codebase subgraph
  - `GOVERNS` must have a `weight` > 0
- Validation queries that detect violations
- What the graph-reviewer agent checks and how it approves/rejects a graph

### 3.4 Create docs/graph/seeding-rules.md

**File:** `docs/graph/seeding-rules.md`

Describe:
- Seeding generates a useful initial graph from a codebase, not just a reference index
- The goal: produce a graph useful for reasoning about business logic and constraints, not just finding which files reference which
- What `/grasp` produces: codebase structure (files, functions, classes, endpoints, call graph, import graph)
- What `/grasp-domain` produces from that: domain decomposition, feature grouping, operation identification, actor inference, business rule detection
- What `/grasp-po` adds: PO-validated feature descriptions, actor permissions/restrictions, business rules, decisions, constraints
- Seeding quality bar: a new codebase analyzed by `/grasp --full` + `/grasp-domain` should produce a graph where:
  - At least 3 domains are identified
  - Each domain has at least one feature with a meaningful summary
  - Features have operations with names that reflect business intent (not just function names)
  - Actors are identified and linked to operations
  - Business rules are surfaced from code patterns (guards, permissions, validation logic)
- What makes seeding fail (e.g., too few entry points detected, no business-looking names, trivial summaries)
- How to improve seeding results: better entry point patterns, more language support, richer domain-analyzer prompts
